# ADR-020: Estratégia de Access Tokens e Refresh Tokens com Rotação Mandatória## StatusAprovado## ContextoPara manter sessões interativas em clientes mobile e web sem expor repetidamente as credenciais do usuário e sem criar gargalos de verificação centralizada para todas as requisições HTTP, é necessária uma arquitetura de tokens com separação clara de responsabilidades: autorização stateless de curta duração e manutenção de sessão stateful com rotação contínua.## Decisão1. **Access Tokens (JWT):**   - Assinados com HMAC-SHA256 utilizando segredo exclusivo JWT_ACCESS_SECRET.   - TTL curto de 15 minutos (900 segundos).   - Claims restritas: sub (userId) e sid (sessionId).   - Validação em todas as requisições via JwtAuthGuard global, associando a sessão ativa ao principal autenticado.2. **Refresh Tokens Opaque:**   - Strings aleatórias criptograficamente seguras com 48 bytes (96 caracteres hexadecimais), geradas via crypto.randomBytes(48).   - TTL de 30 dias.   - **Armazenamento Seguro:** Refresh tokens em texto plano NUNCA são armazenados no banco de dados. O banco armazena exclusivamente o hash HMAC-SHA256 do token com pimenta de servidor (REFRESH_TOKEN_PEPPER).3. **Rotação Mandatória de Refresh Token:**   - A cada chamada ao endpoint POST /api/v1/auth/refresh, um novo refresh token e um novo access token são gerados.   - O hash do token anterior é movido para a coluna previousRefreshTokenHash da tabela sessions, e o novo hash é persistido em     efreshTokenHash.4. **Detecção de Reuso e Revogação Imediata:**   - Se uma requisição apresentar um refresh token cujo hash coincida com previousRefreshTokenHash, o sistema detecta que o token já rotacionado foi interceptado ou reusado (potencial ataque de repetição/roubo).   - A sessão inteira é imediatamente revogada (     evokedAt = now()), e um erro 401 AUTH.INVALID_REFRESH_TOKEN é retornado.## Consequências- **Positivas:**  - Janela de exposição mínima para access tokens (15 minutos).  - Isolamento de vazamentos: se o banco de dados for comprometido, os hashes dos refresh tokens com pepper não permitem obter os tokens em texto plano.  - Mitigação de replay attacks e roubo de tokens com revogação automática.- **Negativas / Mitigações:**  - Requer que o cliente atualize e persista o novo par de tokens a cada renovação.
